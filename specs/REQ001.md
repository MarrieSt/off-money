# Money — Initial Application Specification

## 1. Purpose

Build a new standalone Django application for personal finance analytics at:

`https://money.sokoloff.co.uk`

The application will eventually ingest transaction data from an Emma-generated Google Sheet, store a durable transaction history, calculate day-by-day spending analytics, support configurable definitions of spend / no-spend days, and provide motivating streaks and rewards.

This first implementation phase is intentionally narrower.

**Phase 1 must create the application foundation only:**

- standalone Django project;
- local PostgreSQL database for development;
- Neon PostgreSQL database for production;
- independent Django authentication and user model;
- database schema suitable for the future transaction import and analytics features;
- Django Admin screens for all core domain objects;
- simple generic frontend views proving the application and data model work;
- blue-toned visual identity;
- deployment-ready configuration;
- no Google Sheets ingestion yet;
- no spend calculations yet;
- no dashboard/charts yet.

When Phase 1 is deployed, the site should be a clean, mostly empty Money application shell that can be populated through Django Admin and used as the basis for subsequent dashboard work.

# 2. Architectural Principles

## 2.1 Money is completely independent from Culture

Money must not be implemented as an app inside the existing Culture Django project.

It should have its own:

- GitHub repository;
- Django project;
- Railway service/project;
- database;
- Neon project/database;
- user table;
- migrations;
- environment variables;
- deployment lifecycle.

There must be no runtime or database dependency on `culture.sokoloff.co.uk`.

The only relationship is that both applications live under the `sokoloff.co.uk` domain family.

## 2.2 Keep v1 deliberately simple

Do not introduce infrastructure that is not yet required.

Do **not** add Redis, Celery, Kafka, dbt, Airflow, a data warehouse, microservices, REST APIs, React, or a separate frontend framework in Phase 1.

Use standard Django server-rendered views/templates and PostgreSQL.

## 2.3 Preserve raw financial history

Future business rules must not mutate imported source transactions.

The eventual processing model should be:

```text
SOURCE TRANSACTION
       ↓
NORMALISED / STORED TRANSACTION
       ↓
CLASSIFICATION / RULES
       ↓
SPEND ELIGIBILITY
       ↓
NO-SPEND ELIGIBILITY
       ↓
DAILY ANALYTICS
       ↓
STREAKS / REWARDS / DASHBOARDS
```

Phase 1 should design the schema so this later layering is straightforward.

# 5. Authentication and User Model

Create a custom Django user model **from the first migration**.

Do not use Django's default User model and attempt to replace it later.

A minimal implementation is sufficient, based on `AbstractUser`.

Suggested model:

```text
MoneyUser
- id
- username and/or email
- first_name
- last_name
- is_active
- is_staff
- date_joined
```

It is acceptable to use username/password login in Phase 1.

Google login is **not** part of Phase 1.

Google service-account authentication for the future Sheet importer is unrelated to user login and must not be coupled to the Money user authentication model.

All finance-domain records must ultimately belong to a user.

# 6. Core Data Model

Create the following models in Phase 1.

Use sensible Django field types, indexes, foreign keys, constraints, `created_at`, and `updated_at` timestamps where appropriate.

## 6.1 FinancialAccount

Represents an account/card/source represented in Emma.

Suggested fields:

```text
FinancialAccount
- id
- user -> MoneyUser
- source_name
- display_name
- institution_name
- account_type (optional / flexible choice)
- currency (default GBP)
- is_active
- include_in_analytics (default True)
- include_in_no_spend_tracking (default True)
- sort_order (optional)
- created_at
- updated_at
```

Requirements:

- `source_name` stores the account name received from Emma.
- `display_name` allows Money to later show a friendlier local name without changing the imported source value.
- An account can be excluded from analytics or no-spend tracking without deleting it.
- Add a useful uniqueness constraint per user where appropriate, for example `(user, source_name, institution_name)`.

## 6.2 Transaction

This is the central durable transaction record.

The current Emma `Primary` sheet contains these source fields:

```text
ID
Date
Amount
Account
Bank
Currency
Category
Subcategory
Type
Tags
Counterparty
Custom Name
Merchant
Additional details
Notes
Linked transaction ID
```

Design the model so these can be imported without loss.

Suggested fields:

```text
Transaction
- id                              # local DB primary key
- user -> MoneyUser
- account -> FinancialAccount

- source_transaction_id           # Emma ID
- transaction_date
- amount
- currency

- source_category
- source_subcategory
- source_type
- source_tags
- source_counterparty
- source_custom_name
- source_merchant
- source_additional_details
- source_notes
- source_linked_transaction_id

- raw_data JSONField

- source_created_at (optional; leave nullable if unavailable)
- imported_at (nullable in Phase 1)
- last_source_sync_at (nullable)
- created_at
- updated_at
```

Important requirements:

- Use `DecimalField`, never float, for money.
- Preserve signed amounts as supplied by Emma.
- Do not derive a `spend` boolean directly into the raw transaction record.
- `source_transaction_id` should be indexed and unique within the source/user scope.
- `raw_data` should eventually hold the original imported row as JSON for traceability.
- The application must support transactions being updated on subsequent source syncs rather than assuming imported data is immutable.
- Add indexes that will support future queries by user/date, account/date, category/date, and source transaction ID.

## 6.3 SpendRule

Create this model now even though no evaluation engine is required in Phase 1.

Purpose: later define whether certain accounts, categories, transaction types, merchants, etc. count as spend and/or count against a no-spend day.

Suggested fields:

```text
SpendRule
- id
- user -> MoneyUser
- name
- rule_scope
- match_field
- match_operator
- match_value
- action
- priority
- is_active
- created_at
- updated_at
```

Initial choices can be simple and extensible.

Example `match_field` choices:

- account
- category
- subcategory
- type
- merchant
- counterparty

Example actions:

- INCLUDE_IN_SPEND
- EXCLUDE_FROM_SPEND
- INCLUDE_IN_NO_SPEND
- EXCLUDE_FROM_NO_SPEND

Do not implement the rule evaluator yet.

## 6.4 DailyStatus

Create the future summary model but do not calculate/populate it automatically yet.

Suggested fields:

```text
DailyStatus
- id
- user -> MoneyUser
- date
- total_outflow
- qualifying_spend
- qualifying_transaction_count
- is_no_spend_day
- calculation_version (optional)
- calculated_at
- created_at
- updated_at
```

Constraint:

- one DailyStatus per `(user, date)`.

This model will later support calendar views and streak calculations.

## 6.5 RewardDefinition

Represents configurable reward/achievement definitions.

Suggested fields:

```text
RewardDefinition
- id
- user -> MoneyUser
- name
- description
- reward_type
- threshold
- is_active
- created_at
- updated_at
```

Examples for later phases:

- 3 consecutive no-spend days
- 5 consecutive no-spend days
- 10 no-spend days in a month
- beat previous monthly record

Do not implement award calculation yet.

## 6.6 EarnedReward

Create a minimal model for future achievement history.

```text
EarnedReward
- id
- user -> MoneyUser
- reward -> RewardDefinition
- earned_on
- metadata JSONField
- created_at
```

No automatic creation in Phase 1.

# 13. Future Analytics Architecture — DOCUMENT ONLY

The main future analytical unit is a **day**, not merely a transaction list.

Expected future capabilities:

### Daily spend

For each day show:

- total outflow;
- qualifying spend;
- spend by account;
- spend by category;
- transaction count;
- drilldown to underlying transactions.

### No-spend logic

A no-spend day must be rule-driven.

Example exclusions may later include:

- transfers;
- investments;
- mortgage/housing;
- utilities;
- insurance;
- subscriptions;
- selected accounts;
- selected categories.

The system must therefore distinguish concepts such as:

```text
transaction exists
is outflow
counts as financial spend
counts against no-spend day
```

These concepts must not be collapsed into one hard-coded boolean on `Transaction`.

### Rewards

Future examples:

- current no-spend streak;
- longest streak;
- N no-spend days per month;
- monthly personal record;
- achievements;
- comparison against rolling historical spending behaviour.

# 19. Product Direction Summary

This project is intended to evolve into a personal finance behavioural analytics application rather than a traditional budgeting app.

The eventual product should answer questions such as:

- How much did I spend yesterday?
- Which account did it come from?
- Which categories contributed to it?
- What individual transactions made up that number?
- Which spending should count against a no-spend day?
- How many no-spend days have I achieved this month?
- What is my current and best streak?
- How is my discretionary spending changing over time?

Phase 1 should create a clean, trustworthy foundation for those capabilities without prematurely implementing them.

Clarifications 

Q: For Phase 1, should users sign in with username/password, and should accounts be created only through Django Admin?
A: Username; Admin-created - Smallest, explicit setup; no public signup.
Q: Can a transaction exist without an Emma source ID, for example when manually seeded in Admin?
