# Money — Transaction Delta Ingestion & Reconciliation Specification

## 1. Objective

Implement scheduled and manually-triggerable transaction ingestion for `money.sokoloff.co.uk`.

The local Money database must remain aligned with the Emma Google Sheets transaction source while avoiding unnecessary full-history imports throughout the day.

The ingestion system must use a single idempotent reconciliation engine with different reconciliation windows depending on the job type.

---

## 2. Core Principle

Do not implement separate ingestion logic for intraday, daily, and monthly jobs.

All jobs must call the same reconciliation service, conceptually:

```python
reconcile_transactions(start_date=None, end_date=None, full=False)
```

The scheduler or manual trigger determines the date window. The reconciliation engine handles reading Emma data, normalisation, matching, inserts, updates, missing records, logging, and errors.

Running the same reconciliation repeatedly must be safe and must not create duplicate transactions.

---

## 3. Scheduled Jobs

All business schedules are defined in the `Europe/London` timezone.

### 3.1 Intraday Refresh

Run every 3 hours during the day:

- 06:00
- 09:00
- 12:00
- 15:00
- 18:00
- 21:00

Reconciliation window:

- Current date
- Previous 3 calendar days

The implementation should deliberately include a small overlap rather than attempt a precise delta since the previous execution.

Purpose:

- Import newly-arrived Emma transactions.
- Pick up changes to recent transactions.
- Correct categorisation or merchant changes made during the day.
- Provide reasonably fresh dashboard data without repeatedly processing the entire history.

---

### 3.2 Daily Rolling Reconciliation

Run at:

```text
03:00 Europe/London
```

Reconciliation window:

```text
today - 3 calendar months → today
```

Use calendar-month arithmetic rather than a fixed 90-day approximation.

Purpose:

- Reconcile recent transaction history against Emma.
- Capture delayed Emma changes.
- Correct categories, merchants, accounts, dates, amounts, or other mutable source fields.
- Detect locally-stored transactions that have disappeared from the Emma source within the reconciliation window.

Exception:

- Do NOT run this job on the 3rd calendar day of the month.
- The monthly full reconciliation supersedes it on that date.

The application must enforce this skip itself. Do not rely solely on Railway scheduling configuration to prevent the daily reconciliation from running.

---

### 3.3 Monthly Full Reconciliation

Run:

```text
00:00 on the 3rd day of every month
```

Reconciliation window:

```text
entire available Emma transaction history
```

Purpose:

- Perform authoritative full-source reconciliation.
- Detect historical changes outside the rolling three-month window.
- Detect missing historical transactions.
- Repair any drift between Emma and the Money database.

After the full reconciliation completes, normal intraday jobs should continue at 06:00, 09:00, 12:00, 15:00, 18:00, and 21:00.

---

## 4. Reconciliation Behaviour

For the selected source window:

1. Fetch all Emma transaction rows belonging to the requested window.
2. Parse and normalise source data.
3. Resolve reference entities such as account, institution/bank, category, merchant, and currency using the existing Money data model.
4. Identify the corresponding local transaction using the existing stable source identifier / transaction key.
5. Compare the complete source-controlled transaction state against the local record.
6. Insert new transactions.
7. Update existing transactions whose Emma-controlled fields changed.
8. Leave identical transactions unchanged.
9. Detect local Emma-sourced transactions in the reconciliation window that are no longer present in the source dataset.
10. Record execution statistics and errors.

The Emma source is authoritative for fields imported from Emma.

Application-owned fields must not be overwritten unless explicitly defined as source-controlled.

---

## 5. Transaction Matching

Use the existing stable Emma/source transaction identifier where available.

The matching key must be deterministic and unique enough that:

- repeated imports do not create duplicates;
- edits to mutable transaction fields do not cause a transaction to appear as a new transaction;
- a reconciliation can reliably determine whether an existing transaction changed.

Do not use mutable values such as category or merchant name as the sole identity mechanism.

If the existing ingestion implementation already generates a deterministic transaction hash/ID, reuse it unless there is a demonstrated identity problem.

---

## 6. Missing Transactions

Do not automatically hard-delete transactions when they disappear from Emma.

Transactions sourced from Emma should support an ingestion/source state such as:

```text
active
missing
```

During reconciliation:

- A local Emma transaction present in the current source window remains `active`.
- A local Emma transaction within the authoritative reconciliation window but absent from the complete Emma source result for that window becomes `missing`.
- If a previously missing transaction later reappears, restore it to `active`.

Missing detection must only run when the importer knows it has successfully obtained a complete source dataset for the requested reconciliation window.

If the Google Sheets read fails, is incomplete, or cannot be validated, the system must NOT mass-mark transactions as missing.

Dashboards should normally exclude `missing` transactions from spend calculations while retaining them for audit/history purposes.

---

## 7. Date Handling

Emma spreadsheet dates must be parsed explicitly according to the known source convention.

Do not rely on locale-dependent automatic date parsing.

Normalise transaction dates into a consistent internal date representation before comparison or persistence.

Scheduling/business-date calculations must use:

```text
Europe/London
```

This is required to handle BST/GMT transitions correctly.

---

## 8. Idempotency

Every reconciliation must be idempotent.

Running the same job multiple times over the same source state must result in:

```text
created = 0
updated = 0
missing = 0
restored = 0
unchanged = N
```

except for legitimate source changes occurring between executions.

Database writes should use bulk operations where practical. Do not perform one Google Sheets API request per transaction row.

The source sheet should be read in batches / ranges suitable for the reconciliation window, then processed locally.

---

## 9. Concurrency / Job Locking

Two reconciliation jobs must not modify the same dataset concurrently.

Before starting a reconciliation, acquire an application/database-backed ingestion lock.

If another reconciliation is already running:

- scheduled execution should exit cleanly and log `skipped_locked`;
- manual execution should clearly report that another reconciliation is currently running;
- do not start a second overlapping reconciliation.

The lock must recover safely from worker/process crashes. Prefer a database advisory lock or a persisted job-lock mechanism with safe expiry/recovery rather than an in-memory lock.

---

## 10. Ingestion Run Audit Model

Create or extend an ingestion-run model so every execution is observable.

Suggested fields:

```text

job_type                  # intraday / daily / full / manual
trigger_type              # scheduled / manual_admin / manual_cli
requested_start_date
requested_end_date
started_at
finished_at
status                    # running / success / partial / failed / skipped
rows_read
transactions_created
transactions_updated
transactions_unchanged
transactions_missing
transactions_restored

error_summary

```

Optional but useful:

```text
duration_ms
source_snapshot_metadata
code_version / deployment identifier
```

Admin users must be able to inspect previous runs and their statistics.

---

## 11. Error Handling

A malformed individual transaction should not necessarily abort the entire reconciliation.

Where safe:

- log the failed row;
- increment `rows_failed`;
- continue processing other transactions;
- mark the overall run `partial` if some rows failed.

Infrastructure/source failures that make the source dataset incomplete should fail the run and prevent missing-transaction detection.

Errors must be visible in Railway logs and in the ingestion-run audit record.

Never log Google credentials, access tokens, service-account private keys, or other secrets.

---

## 12. Manual Execution

All three standard reconciliation modes must be manually triggerable for development, testing, and support.

### 12.1 Django Management Command

Provide a management command such as:

```bash
python manage.py reconcile_transactions --mode intraday
python manage.py reconcile_transactions --mode daily
python manage.py reconcile_transactions --mode full
```

Also support an explicit custom date range:

```bash
python manage.py reconcile_transactions --start 2026-09-01 --end 2026-09-30
```

Useful options:

```bash
--dry-run
--verbose
```

`--dry-run` should perform source reading, parsing, matching, and comparison but must not persist transaction/reference changes or missing-state changes.

Manual `--mode daily` execution should run when explicitly requested even if the current date is the 3rd. The "skip daily on the 3rd" rule applies to scheduled execution, not intentional manual testing.

---

### 12.2 Django Admin

Add an Ingestion / Reconciliation section to Django Admin.

Provide clearly-labelled manual actions/buttons for:

- Run Intraday Reconciliation
- Run 3-Month Reconciliation
- Run Full Reconciliation

The admin must show a confirmation screen before starting a full reconciliation.

After triggering, show the resulting run record/status rather than leaving the user uncertain whether the request started.

Do not run a potentially long full reconciliation synchronously inside a normal HTTP request if that risks HTTP/request timeouts. The admin action may dispatch the same command/service through the project's background execution mechanism if required.

---

## 13. Optional Manual Test Range UI

If straightforward, provide an admin form allowing an authorised user to select:

```text
start date
end date
dry run yes/no
```

and trigger reconciliation for that range.

This is useful for testing historical behaviour without performing a full reconciliation.

## 14. Scheduled Entry Points

Expose scheduler-safe Django management commands/arguments so Railway Cron services can invoke the jobs directly.

Recommended commands:

```bash
python manage.py reconcile_transactions --mode intraday --scheduled
python manage.py reconcile_transactions --mode daily --scheduled
python manage.py reconcile_transactions --mode full --scheduled
```

The `--scheduled` flag allows application-level schedule guards to be applied.

For example, scheduled daily mode must check the London calendar date and exit successfully without reconciliation when `day == 3`.

Manual commands must not be blocked by this guard.

## 16. Railway UTC / DST Requirement

Before configuring cron expressions, verify Railway's current cron timezone semantics.

If Railway Cron schedules are evaluated in UTC, do NOT assume a static UTC cron expression permanently equals the desired Europe/London time because the UK changes between GMT and BST.

Preferred architecture in that case:

- Railway triggers jobs at safe UTC candidate times/frequencies.
- The Django command evaluates `Europe/London` time and decides whether the business schedule is due.

Alternatively, maintain separate GMT/BST Railway schedules only if operationally preferable and documented.

The business requirement is authoritative: executions should correspond to the specified Europe/London schedule.

---

## 17. Performance Requirements

The previous ingestion approach must not perform Google Sheets reads row-by-row.

Requirements:

- Fetch source rows in bulk.
- Resolve reference data efficiently.
- Preload existing transaction identifiers for the requested reconciliation window.
- Compare records in memory where practical.
- Use bulk insert/update operations where practical.
- Avoid repeated database queries for the same account/category/merchant/reference entity.

Log duration and row counts so performance can be measured.

A reconciliation of thousands of rows should not require hours solely because of per-row Google API calls.

---

## 18. Observability

Each run should produce concise structured logs similar to:

```text
reconciliation_started mode=daily start=2026-07-04 end=2026-10-04
source_rows=8123
created=12
updated=43
unchanged=8061
missing=4
restored=2
failed=1
duration=18.4s
reconciliation_finished status=partial
```

Railway logs and Django Admin ingestion history should make it easy to answer:

- Did the job run?
- Which window did it reconcile?
- How long did it take?
- How many rows were read?
- What changed?
- Did anything fail?

---

## 19. Security

Manual ingestion controls must be restricted to authorised staff/admin users.

Google credentials and database credentials must remain environment variables / secrets and must never be persisted in ingestion logs.

Dry-run output must also avoid exposing secrets.

---

## 20. Acceptance Criteria

The feature is complete when:

1. Intraday reconciliation can process the recent 3-day window.
2. Daily reconciliation can process the rolling previous 3 calendar months.
3. Full reconciliation can process the entire Emma history.
4. All modes use the same reconciliation engine.
5. All modes can be manually triggered from the Django management command.
6. Standard modes can be triggered from Django Admin.
7. A custom date-range reconciliation can be manually tested.
8. Re-running an unchanged window creates no duplicate transactions and produces no unnecessary updates.
9. Changed Emma transactions update their corresponding local records.
10. New Emma transactions are inserted.
11. Transactions absent from a successfully-read authoritative source window are marked missing rather than deleted.
12. Missing transactions that reappear are restored.
13. Incomplete/failed source reads cannot cause mass missing-state updates.
14. Scheduled daily reconciliation skips itself on the 3rd of each month.
15. Monthly full reconciliation runs on the 3rd.
16. Concurrent reconciliations are prevented.
17. Every run produces an auditable run record with useful statistics.
18. Google Sheets data is fetched in bulk rather than row-by-row.
19. Scheduling honours Europe/London business times across GMT/BST.
20. Railway logs clearly expose execution outcome and duration.
