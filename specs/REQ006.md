# REQ004 --- Good Behaviour Calendar

## 1. Purpose

Add a **Good Behaviour Calendar** to the Money Overview dashboard,
directly below the existing Spending chart.

The calendar gives an immediate month-level view of spending behaviour.
Each calendar day is colour-coded according to the **total qualifying
spend for that day**, using exactly the same transaction
inclusion/exclusion logic as the existing Spending chart.

The selected UI direction is **Option C: calendar with daily totals +
mini transaction bars**.

The feature should answer two questions very quickly:

1.  **How well am I doing this month?**
2.  **What caused a particular good/bad day?**

------------------------------------------------------------------------

## 2. Placement

On the **Overview** page:

1.  Existing Spending chart
2.  **Good Behaviour Calendar**
3.  Existing Recent Transactions section

The calendar should use the same maximum content width, card styling,
typography, spacing, borders and visual language as the Spending widget.

------------------------------------------------------------------------

## 3. Default State

On page load:

-   Display the **current calendar month**.
-   Week starts on **Monday**.
-   Show Monday--Sunday columns.
-   Current day should have a subtle visual marker/border.
-   Future dates in the current month must appear inactive/neutral and
    must **not** be classified as good or bad.
-   Padding dates from the previous/next month may be shown to complete
    the calendar grid, but must be visually muted.
-   No day needs to be selected initially.

Header example:

`GOOD BEHAVIOUR`

`October 2026`

Controls on the right:

`‹   ›   Today`

The user can navigate backward/forward by whole calendar months. `Today`
returns to the current month.

------------------------------------------------------------------------

## 4. Daily Spend Calculation

The calendar must **not create its own definition of spending**.

For every date, calculate the daily total using the same underlying
transaction filtering and spend logic used by the Spending chart.

This includes, where applicable:

-   transaction eligibility;
-   handling of positive/negative values;
-   exclusions;
-   account treatment;
-   transaction status;
-   category/rule treatment;
-   any future changes to the Spending chart's spend definition.

The Spending chart and Good Behaviour Calendar should ideally consume a
**shared service/query/domain function** so their totals cannot drift
apart.

### Consistency requirement

For any date:

> Calendar daily total = Spending chart daily total for the same date
> under the same spend logic.

Do not duplicate the business rules independently in the calendar
implementation.

------------------------------------------------------------------------

## 5. Behaviour Bands

Each completed/current calendar day receives a background colour
according to its qualifying spend.

  -----------------------------------------------------------------------
  Daily spend             Behaviour               Visual treatment
  ----------------------- ----------------------- -----------------------
  **£0.00**               Excellent / no-spend    Strong positive green
                          day                     

  **£0.01--£50.00**       Good / low-spend day    Soft green-to-amber /
                                                  light amber

  **£50.01--£150.00**     Higher-spend day        Deeper amber / orange

  **£150.01+**            Bad / high-spend day    Red
  -----------------------------------------------------------------------

### Important boundary rules

-   Exactly **£0** → green
-   Exactly **£50.00** → low-spend band
-   **£50.01** → medium-spend band
-   Exactly **£150.00** → medium-spend band
-   **£150.01+** → red

Use accessible text/background contrast. Colour should be prominent
enough that the monthly pattern is obvious at a glance, but still fit
the existing restrained Money UI.

Do not rely on colour alone: the numeric daily total is also displayed.

------------------------------------------------------------------------

## 6. Calendar Day Cell

Each active day cell should contain:

### 6.1 Date

Day number at the top.

Example:

`8`

### 6.2 Daily spend total

Display the qualifying spend beneath the date.

Examples:

`£0`

`£23`

`£98`

`£206`

Whole-pound display is sufficient in the compact calendar cell. Exact
pence can be shown in the drill-down.

### 6.3 Mini transaction bars

At the bottom of the cell, show a tiny bar/spark-style representation of
the day's qualifying transactions.

The intention is **context, not precision**.

Requirements:

-   Each bar represents an individual qualifying transaction or a
    sensible compact aggregation if there are too many transactions to
    display cleanly.
-   Bar height should loosely communicate transaction magnitude relative
    to other transactions on that day.
-   Use the existing spending/category colour language where practical.
-   Keep the graphic extremely lightweight; it must not compete with the
    daily total.
-   £0 days have no bars.

The mini bars should make days such as these visually distinct:

-   £100 from one transaction;
-   £100 spread across many small transactions.

------------------------------------------------------------------------

## 7. Interaction --- Selecting a Day

The entire day cell is clickable.

When a user selects a day:

-   visually highlight the selected cell;
-   open a **day detail panel**;
-   show the exact qualifying spend total;
-   show the transactions contributing to that total.

On desktop, the preferred interaction is an **inline/right-side detail
panel associated with the calendar**, as shown in Option C.

The calendar may reduce its grid width while the detail panel is open,
provided day cells remain readable.

The panel should be dismissible with an `×`.

Selecting another date updates the panel without a full-page navigation.

------------------------------------------------------------------------

## 8. Day Detail Panel

### Header

Example:

`Thursday, 8 October 2026`

### Total

Example:

`£206.14`

Use the same behaviour-band colour treatment as the selected calendar
day.

Optional supporting label:

`High spend day`

or

`No-spend day`

### Intraday mini chart

Above the transaction list, show a small timeline/bar chart representing
the day's qualifying transactions across the day where transaction time
is available.

If transaction time is not available/reliable, omit the time axis rather
than inventing timestamps.

### Transactions

List all transactions included in the day's spend calculation.

Each row should use the application's existing transaction presentation
where possible and include useful information such as:

-   merchant/description;
-   category;
-   account, if useful;
-   amount;
-   transaction time, if available.

Example:

`Booking.com`\
`Holidays · 10:14`\
`£144.31`

The transaction amounts in the panel must reconcile to the exact
displayed daily total.

Provide:

`View all transactions →`

This should navigate to the Transactions view filtered to the selected
date where the existing transaction page architecture supports
query/filter state.

------------------------------------------------------------------------

## 9. £0 Day Behaviour

A £0 day is a first-class positive state.

The cell should:

-   use the strongest positive green;
-   show `£0`;
-   contain no transaction bars.

When clicked, the detail panel should show a positive empty state rather
than an error or generic blank transaction state.

Example:

`£0.00`

`No-spend day`

`No qualifying spending transactions on this day.`

------------------------------------------------------------------------

## 10. Future Dates

Future dates must:

-   use a neutral/muted background;
-   not show `£0`;
-   not be coloured green;
-   not count as successful no-spend days;
-   not be clickable for transaction drill-down unless there is a future
    use case requiring it.

This prevents future days from artificially making the month look
successful.

------------------------------------------------------------------------

## 11. Previous Months

The user can navigate to historical months using the previous-month
control.

Historical months use exactly the same thresholds and spend logic.

When browsing a historical month:

-   the forward arrow remains available until the current month;
-   navigation beyond the current month should be disabled unless
    explicitly needed later;
-   `Today` returns directly to the current month.

------------------------------------------------------------------------

## 12. Responsive Behaviour

### Desktop

Preferred layout:

-   full month grid;
-   detail panel opens to the right within the calendar card/section.

### Tablet

The detail panel may appear beneath the calendar if horizontal space
becomes constrained.

### Mobile

Use a single-column layout:

-   calendar first;
-   selected-day detail panel directly below;
-   day cells remain large enough to tap comfortably;
-   mini bars may be simplified if necessary.

Do not introduce horizontal scrolling for the calendar as the default
mobile interaction.

------------------------------------------------------------------------

## 13. Visual Design

Follow the existing Money design system visible on the Overview page:

-   navy/dark blue headings;
-   pale blue-grey page background;
-   white cards;
-   subtle blue-grey borders;
-   small uppercase blue eyebrow labels;
-   restrained shadows;
-   existing serif/display heading treatment;
-   existing control/button styling.

The behaviour colours are intentionally the strongest colours in this
widget because rapid visual recognition is the primary purpose.

Suggested conceptual progression:

`GREEN → PALE AMBER → DEEP AMBER/ORANGE → RED`

Exact colour tokens should be implemented as reusable CSS/design tokens
rather than scattered literal values.

Example semantic tokens:

-   `--behaviour-zero`
-   `--behaviour-low`
-   `--behaviour-medium`
-   `--behaviour-high`
-   `--behaviour-future`

Add hover, selected and accessible text variants as required.

------------------------------------------------------------------------

## 14. Accessibility

-   Do not communicate behaviour using colour alone.
-   Daily total remains visible in every completed/current day.
-   Day cells must be keyboard focusable.
-   Pressing Enter/Space on a focused day opens its details.
-   Selected state must have a non-colour indicator such as a
    border/outline.
-   Provide useful accessible labels, e.g.:
    -   `8 October 2026, £206.14 spent, high spend day`
    -   `6 October 2026, no spend`
-   Ensure behaviour-band colours meet appropriate contrast requirements
    for displayed text.
-   Disabled/future dates must be semantically disabled where
    applicable.

------------------------------------------------------------------------

## 15. Data / Backend Design

Do not calculate the entire calendar by issuing one request/query per
date.

Provide an efficient month-level aggregation.

Conceptually, the backend should be able to return:

``` json
{
  "month": "2026-10",
  "days": [
    {
      "date": "2026-10-01",
      "total_spend": "98.00",
      "transaction_count": 3,
      "transactions": [
        {
          "id": "...",
          "amount": "52.00",
          "category": "...",
          "description": "..."
        }
      ]
    }
  ]
}
```

The exact API/view structure may follow the existing Django
architecture.

### Performance

-   Fetch/aggregate the visible month in one logical operation.
-   Avoid N+1 queries.
-   Use database aggregation where sensible.
-   The widget should remain fast even when several years of transaction
    history exist.

Detailed transactions may either be included in the month payload or
loaded on demand when a day is selected. Prefer the approach that best
fits the current Django architecture without unnecessary complexity.

------------------------------------------------------------------------

## 16. Shared Spending Logic

Refactor first if necessary.

If the current Spending chart calculates qualifying spend inside
view-specific code, extract that logic into a reusable
domain/service/query layer before implementing the calendar.

Desired conceptual structure:

``` text
Spending definition / filters
          |
          +---- Spending chart aggregation
          |
          +---- Good Behaviour calendar aggregation
          |
          +---- Selected-day transaction drill-down
```

There must be one source of truth for whether a transaction contributes
to "spending".

------------------------------------------------------------------------

## 17. Acceptance Criteria

The requirement is complete when:

1.  A Good Behaviour Calendar appears directly below the Spending chart.
2.  It defaults to the current calendar month.
3.  Each elapsed/current date shows its daily qualifying spend.
4.  £0 days are green.
5.  £0.01--£50.00 days use the low-spend colour.
6.  £50.01--£150.00 days use the deeper amber/orange colour.
7.  £150.01+ days are red.
8.  Future dates remain neutral and are not treated as £0 days.
9.  Each populated day includes the Option C mini transaction-bar
    visualisation.
10. Clicking a day opens its detail view.
11. The detail view shows the exact total and contributing transactions.
12. The transaction list reconciles exactly to the daily total.
13. Calendar totals reconcile exactly with the Spending chart's logic.
14. Previous months can be browsed.
15. `Today` returns to the current month.
16. The selected day has a clear non-colour selection indicator.
17. £0 days have an intentional positive empty state.
18. The implementation does not perform one backend/database query per
    calendar day.
19. Desktop and mobile layouts are usable.
20. Existing Spending chart behaviour is not regressed.

------------------------------------------------------------------------

## 19. Out of Scope for This Requirement

Do **not** add yet:

-   configurable thresholds;
-   user-defined budgets;
-   streaks;
-   badges/gamification;
-   monthly targets;
-   notifications;
-   comparisons against previous months;
-   account/category filtering unique to this calendar;
-   predictive spending;
-   editing transactions from the calendar.

These can be layered on later once the core calendar is stable.

------------------------------------------------------------------------

## 20. Future-Friendly Considerations

Design the component so later requirements could add:

-   no-spend streaks;
-   monthly score / percentage of green days;
-   threshold configuration;
-   account/category filters;
-   hover summaries;
-   monthly trend comparison;
-   budget overlays;
-   behavioural achievements.

Do not implement these now.

------------------------------------------------------------------------

## 21. UX Reference

The approved direction is **Option C --- Calendar with daily totals +
mini bars**:

-   conventional month grid;
-   strong colour-coded day backgrounds;
-   daily spend visible numerically;
-   tiny transaction bars inside each day;
-   selected-day drill-down with exact total and contributing
    transactions.

The key design principle is:

> **The colour tells me how I behaved; the number tells me how much I
> spent; the mini bars hint at why; clicking tells me exactly what
> happened.**
